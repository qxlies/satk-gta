# Инвентарь: список задач ассета, сверенный с моделью

[English version](../en/inventory.md)

Пакет: `satk.inventory` (MIT); методы разметки живут в `blender/satk_blender/studio/methods/tag.py` (GPL).

## Что это

Модель готова, только когда в ней есть все положенные детали и каждая присоединена к остальным. *Инвентарь*
проекта ассета (`<project>/design/inventory.json`) перечисляет эти детали пунктами: id (`I01`), название, регион обзора,
категория, способ построения, к чему деталь крепится и этап, на котором её строят (G1 форма, G2 сборка, G3
детализация, G4 поверхность). Во время моделирования исполнитель помечает геометрию id пунктов (`scene.tag`), а
`satk asset inventory` говорит про каждый пункт: **built** (построен), **missing** (нет), **unattached** (построен,
но отстоит от родителя) или **rejected** (отклонён ревьюером или помечен на пустом месте) — по живой сессии
Blender или по экспортированной модели. У каждого вида ассета есть стартовый список трёх уровней: `simple` (что
есть у любой стоковой модели этого вида), `standard` (полноценная модель стокового класса) и `hero` (богаче
стока: моторный отсек, полный салон и днище у машины; хлам на крыше, вывески и доделанные задние фасады у здания;
отдельные прицелы и планки у оружия).

## Быстрый пример

```powershell
satk asset init docs-bin --kind prop --detail simple --force
satk inventory validate docs-bin
satk asset inventory docs-bin --plan --md
satk blender session start --project docs-bin --no-resume
satk blender call scene.clear --session docs-bin
satk blender call mesh.primitive --session docs-bin --params '{"kind":"cylinder","segments":8,"radius":0.3,"depth":0.9,"location":[0,0,0.45],"name":"bin"}'
satk blender call scene.tag --session docs-bin --params '{"object":"bin","item":"I01"}'
satk asset inventory docs-bin --session docs-bin
satk blender session stop --name docs-bin
```

Что возвращает восьмая команда (сокращённо):

```json
{"ok":true,"cols":["id","status","name","stage","region","note"],
 "rows":[["I02","missing","Base or feet","G1","base","no geometry carries this id (build it, then scene.tag)"],
         ["I03","missing","Cap or top","G2","top","no geometry carries this id (build it, then scene.tag)"],
         ["I04","missing","Secondary parts","G2","details","no geometry carries this id (build it, then scene.tag)"]],
 "complete":false,"counts":{"built":1,"missing":3,"unattached":0,"rejected":0,"total":4,"required_open":3},
 "source":"session:docs-bin","kind":"prop","detail":"simple"}
```

## Команды

| Команда | MCP | Что делает |
|---|---|---|
| `satk asset init <name> --kind K [--detail simple\|standard\|hero\|none]` | — (`satk_op`) | новый проект получает стартовый инвентарь своего вида (по умолчанию `hero`) |
| `satk inventory starter <kind>\|all [--detail D] [--project P] [--force]` | — (`satk_op`) | стартовый список вида; `--project` записывает его как инвентарь проекта; `all` перечисляет виды |
| `satk inventory validate <project\|file.json> [--strict]` | — (`satk_op`) | понятные ошибки: поля, id, цели и циклы `attaches_to`, категории, этапы, регионы, пункты стартового списка, выброшенные без причины |
| `satk asset inventory <project> [--session S\|--dff F\|--blend F] [--status open\|all\|built\|missing\|unattached\|rejected] [--stage G1..G4] [--plan] [--md] [--strict]` | — (`satk_op`) | отчёт (`complete` = построены все обязательные пункты); `--plan` перечисляет пункты без измерений; `--md` даёт чек-лист |
| `satk inventory mark <project> <id> --reject "<причина>"\|--accept [--by critic]` | — (`satk_op`) | ревьюер отклоняет пункт (он остаётся отклонённым до принятия) или принимает его |
| `satk blender call scene.tag --params '{"objects":[...],"item":"I05"}'` | — (`satk_op`) | пометить объекты целиком; с `select` только эти грани; `clear: true` снимает метки |

## Как это работает

- **Метки.** `scene.tag` пишет целочисленный атрибут граней `satk_item_idx` (0 = без пункта) и свойства объекта
  `satk_item_ids` (список id, на который ссылаются значения; один дописываемый список на сцену, поэтому все
  объекты согласованы) и `satk_item` (id на объекте). Атрибуты граней переезжают вместе с гранями, поэтому метки
  переживают `scene.join`, `kit.fill`, `mesh.attach weld` и MIRROR. Свойство `satk_item`, поставленное вручную, по-прежнему
  относится к непомеченным граням объекта. Правки сетки умеют выбирать помеченные грани: `{"select": {"item":
  "I05"}}`; `{"linked": true}` расширяет выбор до целых сваренных кусков.
- **Измерение.** `scene.items` (только чтение) собирает каждый помеченный пункт из вычисленных сеток (с
  модификаторами): объекты, фреймы, треугольники, размер, связные куски и зазор до каждого пункта, к которому он
  крепится (ближайшие точки в обе стороны через BVH, до 0,3 м). Скрытые, призрачные и опорные объекты, копии
  `*_dam`/`*_vlo` и слоты коллизии, тени и LOD не считаются. Факты пишутся в файл, вердикт выносит сторона MIT.
- **Вердикты.** `rejected`: пункт отклонил ревьюер, он помечен только на скрытых или призрачных объектах, делит
  объект с другими пунктами без меток граней, это заглушка меньше 5 мм или у его граней нет ни одной своей вершины
  (кусок поверхности другого пункта: перекрашенная грань — не деталь). `missing`: геометрии нет, кусков со своей
  геометрией меньше, чем его `count` (пара левый/правый = 2), или — у текстурного пункта (категория `decal`,
  `verify: texture`) — на его гранях нет текстуры-картинки (`verify: paint`: нет ключевого цвета покраски).
  `unattached`: один из его кусков дальше от каждого построенного родителя, чем `max_gap_mm` пункта или допуск его
  категории (панель 30 мм, стекло 25, механизм 60, ходовая 20, остальное 10).
- **Без сессии.** Отчёт читает запущенную сессию проекта, иначе его самый новый чекпойнт разовым запуском
  Blender. Экспортированная модель несёт рядом с DFF файл `<stem>.inventory.json` (инвентарь и факты
  экспортированных фреймов, хеш DFF; пишется при каждом kit export); `--dff` судит по нему и сверяет его с DFF
  (другой хеш, изменённые фреймы, больше помеченных треугольников, чем во фрейме: это проблема, `complete` = false).
  Испорченный файл даёт ошибку `BAD_PARAMS` с подсказкой, а не падение.
- **Инвентарь — это план.** У пунктов стартового списка есть `key`; чтобы выбросить такой пункт (или пометить его
  `required: false`), нужна запись `waived` с причиной из дизайна (иначе `--strict` блокирует); причины про
  время, бюджет, сложность, дальность или видимость не принимаются. Пара сохраняет `count` стартового списка, если
  отказ не называет число дизайна (`{"key", "count", "why"}`). `attaches_to: null` допустим только у оболочки,
  колеса, каркаса или части тела; `max_gap_mm` не больше 150. Вид и уровень детализации задаёт `asset.json`
  проекта. Этап дизайна переименовывает пункты под реальный дизайн и добавляет то, что в дизайне есть.
  `satk asset status` показывает размер инвентаря; `asset check --strict` пользуется отчётом.

## Ограничения и известные проблемы

- Сводное свойство `satk_item` обновляет `scene.tag`; после объединения в нём id цели до следующей метки
  (отчёт читает грани, а не сводку).
- Присоединение меряется между поверхностями: две детали, касающиеся только через третий пункт, считаются
  неприсоединёнными; привязывайте их к этому пункту.
- У видов без «автомобильной» анатомии (пропы, интерьеры, разрушаемые и анимированные объекты) стартовые списки
  общие: переименуйте и разделите пункты на реальные детали.

## Python-API (если другие пакеты его используют)

```python
from satk.inventory import api
rep = api.report("mycar")                       # сессия, иначе самый новый чекпойнт
rep = api.report(None, dff="<work>/out/kit/premier/modloader/premier/premier.dff")   # инвентарь из файла рядом с DFF
rep["complete"], rep["counts"], [i for i in rep["items"] if i["status"] != "built"]
api.has_inventory("mycar")                      # дёшево: есть ли инвентарь у проекта (или у DFF)
from satk.inventory.sidecar import export_sidecar   # им kit export пишет <stem>.inventory.json
```
