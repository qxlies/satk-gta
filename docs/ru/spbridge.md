# spbridge: глаза и руки агента в одиночной GTA:SA

[English version](../en/spbridge.md)

Пакет: `satk.spbridge`.

## Что это

Почти весь моддинг GTA:SA идёт в обычной одиночной игре — стоковый `gta_sa.exe` с модами Mod Loader, ASI и CLEO,
которые MTA не загружает. `spbridge` даёт ИИ-агенту (и человеку) там тот же обзор и управление, что бэкенды MTA и
Ariane в других местах: небольшой плагин **`satk_sp.asi`** отдаёт протокол SAAP/1 по `127.0.0.1` (та же кадрация,
аутентификация и методы, что у моста MTA). Поэтому `satk saap call sp ...` и, позже, вьюер могут управлять
настоящим движком — двигать камеру, задавать время и погоду, снимать скриншот заднего буфера D3D9, определять
сущность под пикселем, запрашивать и осматривать соседние сущности, переключать HUD, а также «руки» `sp.*`
(телепорт, спавн машины/педа/объекта по id модели с запросом стриминга). Плагин только читает память движка и
пишет только PNG-снимки в рабочую папку.

Нативный проект (C++ под MIT, `native/sp_bridge`) собирается инструментами C++ VS; его транспортный слой проверяется
**оффлайн, без игры** — компиляцией хостового SAAP-сервера и прогоном набора тестов соответствия SAAP/1 по TCP
(`satk sp selftest`). Адреса движка 1.0 US собраны в одной таблице (`satk.spbridge.addresses`) и сверяются с базой
знаний и чистым исполняемым файлом.

## Быстрый пример

```powershell
satk sp addresses
satk sp status
```

Что приходит (сокращённо):

```json
{"ok":true,"cols":["name","kind","addr","symbol"],"total":52,"game_version":"1.0us"}
```

<!-- docs-smoke: skip нужны инструменты C++ VS, занимает несколько секунд -->
```powershell
satk sp selftest
```

`satk sp selftest` компилирует хостовый SAAP-сервер (без игры) и прогоняет тесты соответствия SAAP/1 по TCP;
зелёный прогон (`"fail":0`) подтверждает кадрацию, аутентификацию и обработку конвертов в ASI.

## Команды

| Команда | MCP | Что делает |
|---|---|---|
| `satk sp addresses [--verify] [--emit-header]` | — | показать таблицу адресов 1.0 US; сверить с базой знаний; пересобрать заголовок C++ |
| `satk sp build asi\|test\|all` | — | собрать `satk_sp.asi` (x86) и/или хостовый тестовый SAAP-сервер через `cl.exe` |
| `satk sp selftest` | — | оффлайн-проверка: собрать тестовый сервер и прогнать тесты SAAP/1 по TCP |
| `satk sp status` | — | работает ли эндпоинт SP (роль `sp`)? pid, порт, возможности |
| `satk sp start --copy <dir> --yes` | — | запустить **тестовую копию** игры с ASI (нужно согласие, только CLI) |
| `satk sp stop` | — | послать `quit` и убрать файлы обнаружения (нужно согласие, только CLI) |

`sp start`/`sp stop` трогают настоящий процесс игры, поэтому требуют согласия и недоступны агентам через `satk_op`;
они также отказывают для оригинальной установки и чистой копии. Используйте отдельную тестовую копию, сделанную
через `satk game clone --dst <dir>`.

## Как это работает

- **Транспорт**: `satk_sp.asi` слушает `127.0.0.1` и говорит на SAAP/1 — та же кадрация «длина `u32` + JSON»
  (`proto/cpp/saap_frame.hpp`), та же аутентификация `hello` с токеном и те же коды ошибок SAAP. Он пишет
  `work/run/endpoints/sp.json` (`"protocol":"saap/1"`, роль `sp`), поэтому `satk.saap.client` и вьюерный
  `SaapNativeBackend` находят и управляют им без нового транспортного кода.
- **Пул в главном потоке**: ASI переписывает одну инструкцию — `call CGame::Process` внутри `Idle` (`0x53E981` на
  1.0 US) — на трамплин, который выполняет оригинальный тик, а затем раз за кадр обслуживает сокет. Любой метод
  SAAP выполняется в главном потоке игры, поэтому вызовы движка безопасны, а бюджет на кадр крошечный.
- **Методы**: камера (фиксированный режим `CCamera`), окружение (`CClock`/`CWeather`), снимок (задний буфер D3D9 →
  PNG + SHA-256), pick/raycast (`CWorld::ProcessLineOfSight`), `entity.query`/`entity.inspect` (обход пулов педов/
  машин/объектов/зданий/dummy), `log.poll` (собственное кольцо ASI). В замороженном наборе методов SAAP нет спавна
  и телепорта, поэтому они сделаны методами-расширениями `sp.*`, объявленными через возможность `sp.control`.
- **Детерминизм и безопасность**: снимки пишутся только внутрь `SATK_AGENT_OUT_ROOT` (путь вне — `BAD_PARAMS`);
  без токена ASI вообще не слушает; он ничего не патчит, если место хука не является именно `call CGame::Process`,
  поэтому загрузка в другую сборку ничего не делает.
- **Оффлайн-тест**: не зависящий от игры слой сервера (`saap_server.hpp`, `saap_json.hpp`, `saap_sha256.hpp`,
  `saap_png.hpp`) компилируется в консольный тестовый сервер с синтетическим бэкендом; `satk sp selftest` прогоняет
  тесты соответствия SAAP против него по настоящему TCP.

## Ограничения и известные проблемы

- Одна редакция: **1.0 US (HOODLUM)**. Другие сборки `gta_sa.exe` не патчатся (ASI молчит).
- Объём G0: снимок — задний буфер в своём размере (пока без слоёв `capture.size`/`ids`/`depth`); `world.settle`
  стримит вокруг камеры и сообщает `pending: 0` (очередь стриминга не раскрывается).
- Команды `view_*` пока не принимают `--target sp` (в таблице целей вьюера нет роли `sp`); до тех пор
  используйте `satk saap call sp ...`.
- `satk sp start` не выполняется в автоматических сессиях агента; подготовьте команду и запустите её сами на
  тестовой копии.

## Python API (если им пользуются другие пакеты)

```python
from satk.spbridge import addresses, backend
table = addresses.all_symbols()          # таблица адресов 1.0 US
b = backend.sp_backend()                 # SaapNativeBackend для запущенного эндпоинта SP
```
