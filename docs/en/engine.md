# `satk engine`: the MTA fork, setup, dependencies, build

[Русская версия](../ru/engine.md)

Package: `satk.engine`. Rules for an agent working inside the fork: `engine\mtasa\CLAUDE.md`.

## What it is

`engine\mtasa` is our fork of mtasa-blue (GPL-3.0), created **offline** from the local clone `src\mtasa-neon`.
`satk engine` sets it up, keeps the build dependencies under sha256 pins and builds the client (Win32) and the
server (x64) by calling MSBuild directly; build errors come back as rows `file, line, code, msg`. It writes only to
`engine\` and `work\engine\` of the workspace; it does not touch `src\` or the game.

## Quick example

```powershell
satk engine doctor --table
satk engine status
satk engine rc-test --table
```

What comes back from `doctor` (abridged, as JSON):

```json
{"ok":true,"cols":["check","status","msg","fix"],"rows":[["fork","ok","branch main @ e563d3478, base 715ec056d, 2 commit(s) ahead",null]],"status":"ok","summary":"15/15 engine checks ok"}
```

## Commands

| Command | MCP | What it does |
|---|---|---|
| `satk engine doctor [--deep]` | — | 15 checks: checkout, remotes, clean donor, shims, MSBuild/toolset/rc/premake, DXFiles, pins, installed dependencies, solution, key outputs, disk space |
| `satk engine status [--deep]` | `engine` (`cmd=status`) | branch and revision, last builds, pinned dependencies, how many key outputs exist |
| `satk engine setup [--deps] [--offline] [--update-pins] [--reuse-from DIR]` | — | offline clone and remotes, shims and the premake wrapper; `--deps` also installs the client dependencies (downloads, only with your consent) |
| `satk engine rc-test [--control]` | — | compiles the 4 client `.rc` files with `rc.exe` and the `afxres.h` shim; `--control` proves the failure without the shim |
| `satk engine gen` | — | `premake5 vs2026` with `DXSDK_DIR` → `Build\MTASA.sln` (about 5 s) |
| `satk engine build [--project P] [--platform Win32\|x64] [--config Release\|Debug\|Nightly] [--target T] [--jobs N] [--toolset v143]` | `engine` (`cmd=build`) | build; `P` = `server`, `client`, `all`, `changed` or a project name (`"Game SA"`) |
| `satk engine server-smoke` | — | starts the x64 server on `127.0.0.1:22103/22105`, waits until it is ready, `shutdown` |
| `satk engine run CMD --args JSON` | `engine` | the single MCP tool: `status`, `doctor`, `build` |

More `build` options: `--no-deps` (with a project name, do not build referenced projects), `--regen auto|always|never`
(regenerate the projects with premake), `--max-errors` (errors returned; the log has all).

## How it works

**Layout.** `engine\mtasa` is the fork repository (branch `main` from upstream `715ec056d`; `lab/neon` holds Neon,
read-only). Outside the repository live `Directory.Build.targets` and `shims\afxres.h` (MFC is not needed: the shim
is attached to `ResourceCompile` only for projects under `engine\mtasa\`), `satk-premake.lua`, `bootstrap.ps1`,
`deps\` and `deps-lock.json`. These files are generated by `satk engine setup` from
`src/satk/engine/templates`.

**Git.** `neon` points to the local clone `src\mtasa-neon` (fetch only); `upstream` points to GitHub and is not
fetched without your consent (the full history is about 1 GB; `skipFetchAll`). Both have push = `DISABLED`. There is
no `origin` yet: it appears when the fork is published to a private repository.

**Dependencies.** DXFiles, CEF, discord-rpc, rapidjson, Unifont and the closed-source
`net.dll`/`net_64.dll`/`net_arm64.dll`/`netc.dll` are stored once in `engine\deps` (`cache\`, `net\<sha256>\`).
The hashes are in `deps-lock.json`: for CEF, discord-rpc, rapidjson and Unifont these are the upstream pins from
`utils\buildactions`, for DXFiles our own pin, for the net modules "trust on first download". Sources, in order:
the store, verified copies (the fork itself), a download. The premake actions
`install_cef/install_discord/install_unifont/install_data` run through `satk-premake.lua` with `SATK_OFFLINE=1`:
premake gets the files from `deps\` and does not go online. If the CDN serves a different `net.dll`,
`setup --deps` refuses with `REVISION`; a new hash is accepted only explicitly with `--update-pins`.

**Build.** MSBuild is called directly (`-nodeReuse:false`, TEMP/TMP in `<workspace>\work\tmp\engine-build`).
Before a build the tree fingerprint is checked (file list, `premake5.lua`, installed dependencies): if it changed,
the projects are regenerated, because premake expands globs only at generation time. `--project changed` builds what changed since the last successful
build of the platform: an edited `.cpp` → only its project (DLL/EXE), a header or a static library → the whole
solution of the platform, documentation → nothing. Logs: `work\engine\build\logs`. A second parallel build gets
`BUSY`.

Timings on the reference machine (Release): x64 server from scratch 3:00, Win32 client 3:14, one `.cpp` edited in
`Client/game_sa` → `"Game SA"` 2 s, no-op x64 1.5 s. `engine\` takes about 6.8 GB (two configurations).

**Neon.** `engine\mtasa\docs\porting\neon-ledger.toml` is the porting ledger (waves 0-3, PR ranges, predicted
conflicts); `engine\mtasa\docs\limits.toml` lists the engine limits: vanilla / our trunk / Neon.

## Limitations and known issues

- `satk engine` does not start the MTA client. The first client run needs a one-time setup by an administrator; see
  [mta-agent.md](mta-agent.md). `server-smoke` is loopback only, without resources, `ase 0`, no LAN broadcast.
- Names and branding are still upstream's (the fork has not been renamed yet); our own `BRANCH_ID` comes with the
  rename.
- A new MSVC (now 14.51, v145) can break the build before upstream CI notices: fall back to `--toolset v143`
  (MSVC 14.44).
- Every Win32 build relinks `core.dll` (upstream's `gen_language_list` always rewrites its header).
- Low disk space: `satk engine doctor` warns below 12 GB free on the fork's drive; `Build\obj` (about 4.7 GB) can
  be deleted, it is rebuilt.
- Other answers are in [troubleshooting.md](troubleshooting.md).
